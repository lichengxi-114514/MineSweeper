# 设计决策记录（Decision Log）

> 每条记录：决策、选项、理由、代价。答辩时可直接引用。

## D1 雷位存储结构
- 选项：
  - A 一维 bytearray（idx = r*cols + c，配哨兵边框）
  - B 二维 list[list[bool]]
  - C list[bytearray]（每行一个 bytearray）
- 决定：**A**
- 理由（按对本项目的重要性排序）：
  1. **盘面可廉价指纹化。** bytes(arr) 是一次 C 层拷贝，可直接作为
     set/dict 的键；二维结构需 tuple(map(tuple, grid))，是 Python 层
     循环，慢一个量级且占更多内存。这条服务于：测试快照逐字节比对、
     求解器若做状态记忆（R3/回溯）时的去重、examples/ 里用 hex 存期望盘面。
  2. **配合哨兵边框后，邻域枚举在结构上不可能越界。** 分配
     (rows+2)*(cols+2)、真实格从 (1,1) 起，邻域变成对 8 个固定偏移的
     无分支访问，不存在"列首向左绕到上一行行尾"这类安静错误。
     正确性由数据结构保证，而不是靠每个调用点都记得判边界。
  3. **单位格 1 字节，使"用 -1 表示雷"的混编码写法在执行层面被禁止。**
     bytearray 只接受 0..255，误存 -1 立即 ValueError；这正好落实了
     "雷位与邻域数分离存储"的规则，而不是靠自律。
  4. **内存更省。** 100×100 含边框时四份状态（雷位/邻域数/已翻开/
     已插旗）约 41 KB；同规模的二维 bool 结构四份约 340 KB。
     实测见"已验证"。但需说明：9×9～30×24 的规模下两者都远小于
     任何可感知阈值，**因此内存不是选 A 的主要理由**。
  5. **索引是单个整数，便于预计算邻域偏移表与做统一遍历。**
- 代价（明确接受的部分）：
  1. **索引算术错误不会被解释器发现。** 把 r*cols + c 写成 c*rows + r、
     或漏掉哨兵边框导致的 W = cols+2，都会安静地算错而不报错。
     代价性质：调试成本上升。缓解：所有索引只经 idx(r, c) 与
     neighbors() 两个出口生成，禁止裸写 r*cols+c；单元测试覆盖四个角
     与四条边（共 4 角 + 边界中点若干），并与现算版 count_adjacent_raw
     逐格对照。
  2. **可读性与调试不直观。** 打印出来是一串整数，无法看出盘面形状。
     缓解：在 Board.__repr__ 里按行切块渲染（去边框）；不做这一步的话，
     每次调试都要在脑中做索引换算。
  3. **哨兵边框有连带成本。** 布雷候选集必须排除边框格；有效格数从
     rows*cols 变为内部格数，D4 的"候选格不足"判定必须用内部格数；
     邻域数数组也要同样加边框，两套索引必须严格一致。
     缓解：在 Board 内只暴露 (r, c) 语义的接口，边框与 W 不外泄。
  4. **元素是 int 而非 bool。** is_mine 返回的是 0/1，比较必须写
     == 1 或 bool(...)；`is True` 永远为 False 这类错误不会被类型检查
     拦住。缓解：对外一律返回 bool，int 只在 Board 内部流转。
  5. **切片与序列化不直接可用。** a[0:cols] 得到的是 bytearray 而非
     list；写 JSON/文本需显式转换（bytes(a).hex() 或按行渲染）。
     缓解：examples/ 统一用 hex 字符串，导出/导入各写一个函数并有往返测试。
  6. **预计算邻域偏移表在大棋盘上占内存。** 100×100 若存储每格 8 个
     偏移量的嵌套表，约 8 万个整数对象（≈2 MB，因为偏移量超出 CPython
     小整数缓存范围 -5..256）。缓解：小棋盘可预计算，大棋盘退化为
     8 个固定偏移的内联循环；阈值在 perf.md 里给出实测依据。
- 已验证：（待填）sys.getsizeof 实测值；四角与四边的相邻数与现算版一致
- 未验证/待确认：理由 1 的实际收益取决于是否实现 R3 状态记忆；
  若最终放弃 R3，此条应降级为"为测试快照服务"，不宣称求解器收益。

## D2 邻域数字
- 决定：布雷后一次性 O(8N) 预计算并缓存；现算版 count_adjacent_raw() 仅供测试对照。
- 理由：避免"缓存与真值不一致"；查询 O(1)。
- 代价：多 N 字节内存；要求布雷一次完成，不支持增量加雷。
- 缓解：用 500 局随机盘面逐格对照两版本，作为回归测试。
## D3 首点保护范围
- 决定：首点 + 8 邻域（越界裁剪）。
- 理由：保证开局必展开一片 0 区，与"首点安全"卖点一致。
- 代价：候选格减少；中心首点得 9 格安全区、角上仅 4 格，玩家会倾向点中心。
- 数字：9×9 时 mines 上限为中心 72 / 边中 75 / 角 77。
## D4 候选格不足
- 决定：core 抛 ValueError（消息含所需与可用两个数字及首点位置）；
  CLI/GUI 调 core 之前用 max_mines_at(r, c) 预检并给友好提示。
- 理由：不静默改变玩家设定，不破坏 A1"雷数恒定"。
- 代价：需在 core 与 UI 各写一处入口，但判定逻辑只有一份。
- 约束：mines 合法性只能在首点确定后判定，不能在构造时判定。
- 已否决：自动降级为仅保护首点（静默违约）；自动减雷（破坏 A1）。
- 更新（D6=B 之后）：UI 层预检已无必要，构造期上限已保证任何首点可开局。
  Board 层的 max_mines_at 仅用于边界测试与理论上限说明。
## D5 随机入口
- 决定：全部随机性经 core/rng.py 的 make_rng(seed)；rng 由构造函数注入并保存。
- 理由：可复现性可被自动检查；测试稳定；评审可复现截图盘面。
- 代价：构造函数多一个参数；漏传即不可复现。
- 约束：方法内部禁止再次调用 make_rng；除 rng.py 外禁止 import random。
## D6 构造期雷数上界
- 决定：B。构造期校验 0 <= mines <= N - protected_max，
        其中 protected_max = min(rows,3)*min(cols,3)。
- 理由：任何首点都能开局，GUI/CLI 无需预检，测试不必指定首点。
- 代价：9×9 上限由 77 降为 72；任一边 <= 3 且两边都 <= 3 的棋盘上限为 0
        （3×3、2×2、1×3 无法布雷）。写入 README 局限。
- 保留：Board.max_mines_at(r, c) 仍提供单格上限（角 77 / 边 75 / 内部 72），
        用于 Board 层边界测试与理论上限说明，Game 层不使用。
- 已否决：A（存在"点了才知道不行"的 UX 陷阱）。
## D7 A3 比## D7 参考实现 <-> Game 的比对协议（S3c 用）
- 状态源：RefBoard.revealed_numbers().keys() 与 Game.revealed_cells
  均为"累计已翻开集合"，逐次点击后比较集合相等。
- PLAYING 时：每次点击后比较两边集合；同时比较 Game.view(r,c).adjacent
  与 RefBoard.revealed_numbers()[(r,c)]，逐格一致。
- 点到雷：只比对"被点中的那一格被翻开"，不比对"所有雷"。
  Game 在 LOST 时通过 view() 把全部雷标为 mine=True，那是显示职责，不进集合。
- WON 时：停止比对，改判 len(revealed_cells) == rows*cols - mines。
- 集合一律用 set 比较，不断言顺序（参考实现 DFS，正式实现 BFS）。
- 修订：补充 WON 判定与 adjacent 逐格比对；原版本只写集合相等。对协议（Game ↔ RefBoard）
- 决定：以「同一雷位 + 同一点击序列」为原则，逐次比对 delta 与累计集合；
  雷位经 Game.snapshot_mines() 单向取出后喂给 RefBoard。
- 理由（按重要性）：
  1. **两侧必须同源。** RefBoard 的雷位由外部传入，Game 的雷位由 seed + 首点
     决定；不把 Game 的实际雷位取出，就只剩"用同一 seed 各跑一遍"——而两边
     抽样算法不同（rng.sample vs 任何参考写法），盘面必然不同，比对无从谈起。
     因此必须有一个只读出口。
  2. **逐次比对 delta 才能定位失败点。** 只比终局，一旦不一致无法判断是哪一步、
     哪一格出错；A3 要求 1000 局 0 差异，报错必须能直接指向 (局号, 步号, 坐标)。
  3. **三条独立路径互证。** delta 累积、全盘 view() 扫描、ref.revealed_numbers()
     是三条独立通道；任一不一致都能暴露"增量更新漏格"这类只影响累计状态的 bug。
- 协议：
  1. **建立同源**：`g = Game(rows, cols, mines, seed=S)` → `g.reveal(r0, c0)`
     （触发延迟布雷）→ `layout = g.snapshot_mines()` →
     `ref = RefBoard(rows, cols, layout)` → `ref.expand(r0, c0)`。
     第一步即断言 `set(g.reveal(...)) == ref.expand(...)`。
  2. **每步比对三件事**：
     a. delta：`set(g.reveal(r, c)) == ref.expand(r, c)`
     b. 累计：`revealed_by_game == set(ref.revealed_numbers())`
     c. 数字：每个已翻开格 `g.view(r, c).adjacent == ref.revealed_numbers()[(r, c)]`
  3. **点到雷**：`g.reveal` 只返回被点中的那一格（不返回全部雷），状态转 LOST；
     比对 b/c 再跑一次后停止本局。"揭示全部雷"属于显示层（view() 在 LOST 时
     返回 mine=True，GUI 整盘重绘），不进入返回值。
  4. **胜利**：状态转 WON 即停止比对；另用独立断言验证胜利条件
     （已翻开的非雷格数 == rows*cols − mines），而不是复用 Game 自己的判定。
  5. **重复点击已翻开格**：两侧都必须返回空集合，状态与累计集合不变。
  6. **插旗不进入 A3 主体**：A3 全程不插旗；旗与 reveal 的交互由 A6 独立用例覆盖。
  7. **点击序列**：`random.Random(S ^ 0x5EED)` 生成，坐标从"未翻开的格"中取；
     每局上限 min(3N, 200) 步；遇 LOST/WON 提前结束。序列由 seed 完全决定，
     失败可复现。
  8. **规模**：9×9/10 用 seed 0..999；另加 16×16/40、1×9、1×1、2×2（0 雷）、
     3×3（角首点）各 20 局。
- 代价与缓解：
  1. `snapshot_mines()` 是信息泄露入口。缓解：docstring 明示"仅测试与离线分析"；
     `test_architecture.py` 扫描 `src/minesweeper/gui/` 与 `cli.py`，断言不出现
     该方法名——机器可查，不靠自觉。
  2. 断言消息必须含 (seed, 步号, 坐标, 期望集合, 实际集合)，否则 1000 局中一条
     失败无法定位。用 `assert x == y, msg` 显式构造 msg，不依赖 pytest 默认输出。
  3. 比对开销：每步三次比对，9×9 规模预计数秒；若超时，把"全盘 view() 扫描"
     改为每 10 步一次、终局必做一次。
- 已否决：
  1. 同一 seed 让两侧各自布雷——RefBoard 不布雷，且抽样算法不同，盘面必然不同。
  2. 只比终局——无法定位，A3 会退化成"有 3 局失败"而无从下手。
  3. `Game.reveal` 在 LOST 时返回全部雷——与 GUI 整盘重绘重复，且使 delta 比对
     失去意义。
  4. 用 `Board.from_hex` 预置雷位构造 Game——绕过延迟布雷与首点保护，A2 那条
     路径就没被测到。
- 接口影响：`.qoder/rules/00-architecture.md` 的冻结接口新增一行
  `snapshot_mines() -> frozenset[tuple[int, int]]`（仅测试与离线分析用）。
  这是本条唯一批准的接口增补，其余签名不得改动。
- 已定义、待验证：S3c 落地后补"1000 局 0 差异"与总耗时实测。

## D8 Game 的已翻开/已插旗集合表示
- 选项：A set[tuple[int,int]]；B 与 Board 同尺寸的 bytearray 镜像
- 决定：A
- 理由：成员查询 O(1)；len() 即翻开计数，胜负判定 O(1)；
  与外部接口 frozenset 互转零成本；代码直观，无需第二套索引换算。
- 代价：每格约 32B + set 开销。9×9~30×24（≤720 格）下 < 30KB，可忽略；
  100×100 时约 600KB，若将来需要则改 B，索引换算复用 Board 的 _off 语义。
- 已验证：待 S3b 完成后以 tracemalloc 与理论值对比（可选）

## D9 已插旗的格是否阻止 0 区自动展开
- 选项：
  - A 阻止：旗格不翻开、不作为传播源，也不被传播进入
  - B 不阻止：旗仅作标记，展开时照常翻开
- 决定：**A 阻止**
- 理由：
  1. 与 A6「插旗格不可被翻开」的字面一致；选 B 会让 A6 需要加例外。
  2. 与主流实现一致，玩家不必重新学习规则。
  3. 插旗是玩家的显式声明（"我认定这是雷"），程序不应代其推翻。
- 代价：插错旗会切断 0 区，玩家需先取消旗再展开；高雷密度下可能出现
  "一片零区被多面旗切成几块"的观感。写入 README 的规则说明。
- 已否决：B（与 A6 冲突；且"旗插对了反而少翻一片"易被误认为 bug）。
- 验证：tests/test_game.py 中"插旗格参与展开前后状态不变"用例；
  另在 README 规则表中写明本行为。

## D10 LOST 之后越界坐标是否仍抛 IndexError
- 选项：
  - A 抛：越界属调用错误，与对局状态无关
  - B 静默返回 []
- 决定：**A 抛**
- 理由：
  1. 状态守卫不应掩盖编程错误。若 LOST 后静默返回空，GUI 的
     "结束后仍误发点击" 这类 bug 会长期潜伏且难以定位。
  2. 与 reveal 的执行顺序一致：越界判断排在 state 判断之前（契约第 1 步）。
- 代价：GUI 必须自行保证对局结束后不再转发点击。现有
  board_canvas._playing() 已提供该守卫，实现成本为零。
- 已否决：B（以"更宽容"换来了错误可见性的下降，得不偿失）。
- 验证：tests/test_game.py 中 "LOST 后 reveal(-1,0) 仍抛 IndexError" 用例。
