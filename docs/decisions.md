# 设计决策记录（Decision Log）

> 每条记录：决策、选项、理由、代价。答辩时可直接引用。

## D1 雷位存储结构
- 选项：
  - A 一维 bytearray（idx = r*cols + c，配哨兵边框）
  - B 二维 list[list[bool]]
  - C list[bytearray]（每行一个 bytearray）
- 决定：**A**
- 理由（按对本项目的重要性排序）：
  1. **盘面可廉价指纹化。** bytes(arr) 是一次 C 层拷贝，可直接作为
     set/dict 的键；二维结构需 tuple(map(tuple, grid))，是 Python 层
     循环，慢一个量级且占更多内存。这条服务于：测试快照逐字节比对、
     求解器若做状态记忆（R3/回溯）时的去重、examples/ 里用 hex 存期望盘面。
  2. **配合哨兵边框后，邻域枚举在结构上不可能越界。** 分配
     (rows+2)*(cols+2)、真实格从 (1,1) 起，邻域变成对 8 个固定偏移的
     无分支访问，不存在"列首向左绕到上一行行尾"这类安静错误。
     正确性由数据结构保证，而不是靠每个调用点都记得判边界。
  3. **单位格 1 字节，使"用 -1 表示雷"的混编码写法在执行层面被禁止。**
     bytearray 只接受 0..255，误存 -1 立即 ValueError；这正好落实了
     "雷位与邻域数分离存储"的规则，而不是靠自律。
  4. **内存更省。** 100×100 含边框时四份状态（雷位/邻域数/已翻开/
     已插旗）约 41 KB；同规模的二维 bool 结构四份约 340 KB。
     实测见"已验证"。但需说明：9×9～30×24 的规模下两者都远小于
     任何可感知阈值，**因此内存不是选 A 的主要理由**。
  5. **索引是单个整数，便于预计算邻域偏移表与做统一遍历。**
- 代价（明确接受的部分）：
  1. **索引算术错误不会被解释器发现。** 把 r*cols + c 写成 c*rows + r、
     或漏掉哨兵边框导致的 W = cols+2，都会安静地算错而不报错。
     代价性质：调试成本上升。缓解：所有索引只经 idx(r, c) 与
     neighbors() 两个出口生成，禁止裸写 r*cols+c；单元测试覆盖四个角
     与四条边（共 4 角 + 边界中点若干），并与现算版 count_adjacent_raw
     逐格对照。
  2. **可读性与调试不直观。** 打印出来是一串整数，无法看出盘面形状。
     缓解：在 Board.__repr__ 里按行切块渲染（去边框）；不做这一步的话，
     每次调试都要在脑中做索引换算。
  3. **哨兵边框有连带成本。** 布雷候选集必须排除边框格；有效格数从
     rows*cols 变为内部格数，D4 的"候选格不足"判定必须用内部格数；
     邻域数数组也要同样加边框，两套索引必须严格一致。
     缓解：在 Board 内只暴露 (r, c) 语义的接口，边框与 W 不外泄。
  4. **元素是 int 而非 bool。** is_mine 返回的是 0/1，比较必须写
     == 1 或 bool(...)；`is True` 永远为 False 这类错误不会被类型检查
     拦住。缓解：对外一律返回 bool，int 只在 Board 内部流转。
  5. **切片与序列化不直接可用。** a[0:cols] 得到的是 bytearray 而非
     list；写 JSON/文本需显式转换（bytes(a).hex() 或按行渲染）。
     缓解：examples/ 统一用 hex 字符串，导出/导入各写一个函数并有往返测试。
  6. **预计算邻域偏移表在大棋盘上占内存。** 100×100 若存储每格 8 个
     偏移量的嵌套表，约 8 万个整数对象（≈2 MB，因为偏移量超出 CPython
     小整数缓存范围 -5..256）。缓解：小棋盘可预计算，大棋盘退化为
     8 个固定偏移的内联循环；阈值在 perf.md 里给出实测依据。
- 已验证：（待填）sys.getsizeof 实测值；四角与四边的相邻数与现算版一致
- 未验证/待确认：理由 1 的实际收益取决于是否实现 R3 状态记忆；
  若最终放弃 R3，此条应降级为"为测试快照服务"，不宣称求解器收益。

## D2 邻域数字
- 决定：布雷后一次性 O(8N) 预计算并缓存；现算版 count_adjacent_raw() 仅供测试对照。
- 理由：避免"缓存与真值不一致"；查询 O(1)。
- 代价：多 N 字节内存；要求布雷一次完成，不支持增量加雷。
- 缓解：用 500 局随机盘面逐格对照两版本，作为回归测试。
## D3 首点保护范围
- 决定：首点 + 8 邻域（越界裁剪）。
- 理由：保证开局必展开一片 0 区，与"首点安全"卖点一致。
- 代价：候选格减少；中心首点得 9 格安全区、角上仅 4 格，玩家会倾向点中心。
- 数字：9×9 时 mines 上限为中心 72 / 边中 75 / 角 77。
## D4 候选格不足
- 决定：core 抛 ValueError（消息含所需与可用两个数字及首点位置）；
  CLI/GUI 调 core 之前用 max_mines_at(r, c) 预检并给友好提示。
- 理由：不静默改变玩家设定，不破坏 A1"雷数恒定"。
- 代价：需在 core 与 UI 各写一处入口，但判定逻辑只有一份。
- 约束：mines 合法性只能在首点确定后判定，不能在构造时判定。
- 已否决：自动降级为仅保护首点（静默违约）；自动减雷（破坏 A1）。
## D5 随机入口
- 决定：全部随机性经 core/rng.py 的 make_rng(seed)；rng 由构造函数注入并保存。
- 理由：可复现性可被自动检查；测试稳定；评审可复现截图盘面。
- 代价：构造函数多一个参数；漏传即不可复现。
- 约束：方法内部禁止再次调用 make_rng；除 rng.py 外禁止 import random。
## D6 构造期雷数上界
- 决定：B。构造期校验 0 <= mines <= N - protected_max，
        其中 protected_max = min(rows,3)*min(cols,3)。
- 理由：任何首点都能开局，GUI/CLI 无需预检，测试不必指定首点。
- 代价：9×9 上限由 77 降为 72；任一边 <= 3 且两边都 <= 3 的棋盘上限为 0
        （3×3、2×2、1×3 无法布雷）。写入 README 局限。
- 保留：Board.max_mines_at(r, c) 仍提供单格上限（角 77 / 边 75 / 内部 72），
        用于 Board 层边界测试与理论上限说明，Game 层不使用。
- 已否决：A（存在"点了才知道不行"的 UX 陷阱）。
